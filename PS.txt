================================================================================
PROBLEM STATEMENT (PS) EXPLANATION: SHOPPING SESSIONS
================================================================================

1. OVERVIEW & OBJECTIVE
-----------------------
An e-commerce platform logs raw user events (page views, add-to-carts, purchases)
and ad clicks into dirty CSV files. Because users browse across multiple devices,
clear cookies, or log in later, a single person can have many `user_id`s, which
are connected by link logs (`links/*.csv`).

Your goal is to build a high-performance data pipeline (packaged in a Docker
container) that:
  1. Reads and cleans the dirty CSV files from `/data`.
  2. Resolves all linked `user_id`s into canonical "people" (connected components).
  3. Deduplicates and validates events and ad clicks under strict rules.
  4. Groups each person's events into browsing sessions (30-minute inactivity gap).
  5. Attributes each session to the most recent ad click within the prior 7 days
     (Last-Touch Credit) and identifies all campaigns clicked within those 7 days
     (Assists).
  6. Writes two aggregated daily Parquet tables:
     - `/output/user_daily/` (per person, per day)
     - `/output/campaign_daily/` (per campaign, per day)

SCORING & CONSTRAINTS:
- Exactness: The rules are 100% deterministic. "Almost right" scores 0.
  You must pass all 36 edge-case fixtures and the 1M-event dev check (`check-dev`).
- Speed: Your score is container run time in seconds (LOWER IS BETTER).
  - Practice set: ~20 million events (2 submissions/hour).
  - Final evaluation: ~60 million events (hard timeout of 3 minutes; aim for <60s).
- Packaging: Public GitHub repo <= 50 MB with a root `Dockerfile` and no data files.


================================================================================
2. INPUT DATA (/data)
================================================================================
All inputs are mounted read-only at `/data`:

1. `manifest.json`
   - Contains `{"window_start": "...", "window_end": "..."}` in UTC ISO format (F1).
   - Defines the valid time window for the dataset (typically a 14-day window).

2. `products.csv` (Clean)
   - Columns: `product_id,category` (`product_id` is unique).

3. `campaigns.csv` (Clean)
   - Columns: `campaign_id,channel` (`campaign_id` is unique, e.g., `c_123`).

4. `links/*.csv` (Dirty, multiple part files, some header-only)
   - Columns: `user_id_a,user_id_b` (pairs of IDs belonging to the same person).

5. `events/*.csv` (Dirty, 24 to 160 part files, some header-only)
   - Columns: `event_id,user_id,ts,ingest_ts,event_type,product_id,price_cents`

6. `clicks/*.csv` (Dirty, 8 to 48 part files, some header-only)
   - Columns: `click_id,user_id,campaign_id,ts`


================================================================================
3. STRICT CSV & STRING PARSING RULES
================================================================================
Standard off-the-shelf CSV parsers with default settings WILL fail edge cases
unless configured/handled carefully:

- Line endings: ONLY `\n` ends a line. `\r` is treated as a literal character inside
  a field! (e.g., if a line ends with `\r\n`, the last field ends with `\r`, making
  a numeric price like `1000\r` or timestamp `...Z\r` invalid).
- Quotes: Any field may be wrapped in double quotes (`"u1"` -> `u1`, `""` -> empty/null).
  No valid value ever contains a comma, quote, or newline inside it.
  If a quote appears anywhere other than wrapping an entire field (or is unbalanced),
  the line is MALFORMED and must be dropped.
- Field count: A line with too few or too many comma-separated fields, or an empty
  line, is MALFORMED and must be dropped.
- Whitespace & Case: Strings are NEVER trimmed or case-normalized!
  - `" u1"` and ` u1` are the same ID (` u1`), which is different from `u1` and `u1 `.
  - `u1` and `U1` are distinct IDs unless explicitly linked.
- Digits: Only ASCII `0`-`9` count as digits (Unicode digits like `٢٥٠` are invalid).


================================================================================
4. TIMESTAMP PARSING & TIME WINDOWS
================================================================================
All `ts` values in events and clicks must be converted to UTC integer milliseconds
since the Unix epoch. Three formats are valid:

- Form F1: `YYYY-MM-DDTHH:MM:SSZ`
  - UTC, whole seconds only (e.g., `2026-10-03T23:58:10Z`).
- Form F2: `YYYY-MM-DDTHH:MM:SS+HH:MM` or `YYYY-MM-DDTHH:MM:SS-HH:MM`
  - Whole seconds with timezone offset (`00`..`23` hours, `00`..`59` minutes).
  - Subtract the offset to get UTC (`-00:00` is valid UTC).
- Form F3: Digits only (ASCII `0`-`9`), representing epoch milliseconds
  - Leading zeros allowed (e.g., `0001791071890000`).

INVALID TIMESTAMPS (Must drop row):
- Fractional seconds (`2026-10-03T23:58:10.000Z` or `1791071890000.0`), scientific
  notation, negative numbers, lowercase `t` or `z`, space instead of `T`, missing
  colon in offset (`+0200`), out-of-range offset (`+24:00`, `+05:60`).
- Impossible calendar dates: Month 13, Feb 30, Feb 29 on a non-leap year, Hour 24,
  Second 60 (leap second).
- Note: `ingest_ts` in events is guaranteed to always be a valid F1 timestamp.

TIME WINDOWS:
- Events window: `window_start <= ts < window_end`
- Clicks window: `window_start - 7 days <= ts < window_end`
  (7 days = 7 * 86,400,000 = 604,800,000 ms. Clicks up to 7 days before
  `window_start` are kept because they can attribute sessions inside the window.)


================================================================================
5. PIPELINE LOGIC & EXACT PROCESSING ORDER
================================================================================

STEP A: LINKED IDs (Identity Resolution)
----------------------------------------
1. Parse `links/*.csv`: Drop malformed CSV lines and lines where `user_id_a` or
   `user_id_b` is empty.
2. Transitive Closure (Connected Components): If `a,b` and `b,c` exist, `{a, b, c}`
   are all one person. Self-links and duplicate links are harmless.
3. Canonical Person Name: Each person is named by the BYTE-WISE (lexicographically)
   SMALLEST `user_id` in their connected component.
   - IMPORTANT: An ID that appears in `links/*.csv` but NEVER appears in `events`
     or `clicks` still participates in the component and can become the person's
     canonical name if it is the byte-wise smallest!
   - An ID not present in any valid link line is a person of size 1, named by itself.
   - Links are timeless and apply across the entire dataset before sessionization
     and click attribution.

STEP B: EVENTS CLEANING & SESSIONIZATION (Order is critical!)
-------------------------------------------------------------
1. Parse `events/*.csv`: Drop malformed CSV lines and lines where `event_id` is empty.
2. Deduplicate on `event_id` FIRST (Before Validation!):
   - Keep ONLY the copy with the smallest `ingest_ts` (ties in `ingest_ts` have
     identical content).
   - CRITICAL TRAP: Deduplication happens BEFORE field validation! If the earliest
     ingested copy of `event_id` has a bad timestamp, bad price, or empty user_id,
     it wins deduplication and is then dropped in Step 3. A later valid copy with
     a larger `ingest_ts` does NOT rescue it! (However, malformed CSV lines or lines
     with empty `event_id` were already dropped in Step 1, so they never participate
     in deduplication.)
3. Validate the Kept Copy: Drop unless ALL of the following hold:
   - `user_id` is non-empty.
   - `ts` is valid and `window_start <= ts < window_end`.
   - `event_type` is strictly `"view"`, `"cart"`, or `"purchase"` (case-sensitive).
   - `product_id` is non-empty.
   - If `event_type == "purchase"`: `price_cents` must be ASCII digits only, with
     integer value `1 <= price_cents <= 10,000,000` (leading zeros like `0250` -> 250
     are valid).
   - If `event_type` is `"view"` or `"cart"`: `price_cents` is completely ignored
     (even if empty or garbage).
4. Filter Late Events:
   - Drop if `ingest_ts - ts > 24 hours` (`86,400,000` ms).
   - If `ingest_ts - ts <= 86,400,000` ms (including `ingest_ts < ts`), keep it.
5. Sessionize per Person:
   - Map every surviving event's `user_id` to their canonical person ID.
   - Gather all surviving events for the person (across all their linked IDs) and
     sort by `ts` ascending.
   - Walk events in timestamp order: a NEW session starts whenever
     `current_event.ts - previous_event.ts > 30 minutes` (`1,800,000` ms).
   - Events with identical `ts` always stay in the same session.
   - `session_start` = `ts` of the first event in the session.
6. Assign Session Day:
   - Each session belongs to a single UTC date: the UTC calendar date of `session_start`.
   - All events and purchase revenue in that session count toward that start date,
     even if later events in the session cross midnight into the next day!
7. Lookup Product Categories:
   - Map `product_id` using `products.csv`. If a `product_id` is not found in
     `products.csv`, its category is `"unknown"`.

STEP C: CLICKS CLEANING & ATTRIBUTION
-------------------------------------
1. Parse `clicks/*.csv`: Drop malformed CSV lines and lines where `click_id` is empty.
2. Deduplicate on `click_id`: Duplicates have identical values (aside from optional
   CSV quotes); keep one copy per `click_id`.
3. Validate Clicks: Drop unless ALL of the following hold:
   - `user_id` is non-empty.
   - `ts` is valid and `window_start - 7 days <= ts < window_end`.
   - `campaign_id` exists in `campaigns.csv`.
4. Map every valid click's `user_id` to their canonical person ID.
5. Attribution (Per Session):
   For a session belonging to person P with start timestamp `session_start`, find
   all valid clicks belonging to person P (across any of P's linked IDs) that
   fall within the 7-day lookback window:
     `session_start - 604,800,000 ms <= click.ts <= session_start`
   (Note: both endpoints are INCLUSIVE—a click at exact `session_start` or exact
   `session_start - 7 days` qualifies; 1 ms after `session_start` does not.)

   - Credited Campaign (Last-Touch):
     - Pick the qualifying click with the largest (latest) `click.ts`.
     - Tie-breaker: if multiple qualifying clicks share the latest `click.ts`, pick
       the one with the byte-wise smallest `click_id`.
     - If NO qualifying click exists, the session is credited to campaign `"organic"`
       with channel `"organic"`.
     - Note: A single click can credit multiple sessions. Clicks never start, split,
       or merge sessions.

   - Assisting Campaigns (Multi-Touch):
     - Every distinct `campaign_id` among person P's qualifying clicks in
       `[session_start - 7 days, session_start]` assists this session once (even if
       that campaign was clicked multiple times in the window, and INCLUDING the
       campaign that won the last-touch credit).
     - `"organic"` NEVER counts as an assisting campaign (`assisted_sessions = 0`).


================================================================================
6. REQUIRED OUTPUT TABLES (/output)
================================================================================
Write two folders of `*.parquet` files (`day` must be Parquet `DATE` type):

TABLE 1: `/output/user_daily/*.parquet`
One row per `(user_id, day)` that has at least one session starting on `day`.
Columns:
- `user_id` (string): Canonical person name (byte-wise smallest linked ID).
- `day` (DATE): UTC date of session starts.
- `sessions` (integer): Number of sessions for this person starting on `day`.
- `events` (integer): Total surviving events across those sessions.
- `revenue_cents` (integer): Sum of `price_cents` of purchases in those sessions
  (0 if no purchases).
- `top_category` (string, nullable): Category with the highest total purchase
  `price_cents` across those sessions on that day.
  - Tie-breaker: byte-wise smallest category name.
  - If the person had no purchases in sessions starting that day, `null`.
  - `"unknown"` competes like any normal category.

TABLE 2: `/output/campaign_daily/*.parquet`
One row per `(campaign_id, day)` with at least one credited OR assisted session
starting on `day`. (If a campaign only assisted on that day, `sessions`,
`purchasing_sessions`, and `revenue_cents` are `0`).
Columns:
- `campaign_id` (string): Campaign ID, or `"organic"`.
- `channel` (string): Channel from `campaigns.csv`, or `"organic"`.
- `day` (DATE): UTC date of session starts.
- `sessions` (integer): Sessions starting on `day` credited to this campaign.
- `purchasing_sessions` (integer): Credited sessions starting on `day` that contain
  at least one purchase event.
- `revenue_cents` (integer): Sum of purchase `price_cents` in credited sessions
  starting on `day`.
- `assisted_sessions` (integer): Sessions starting on `day` assisted by this
  campaign (`0` for `"organic"`).


================================================================================
7. KEY DATA CHARACTERISTICS & SCALE CHALLENGES
================================================================================
- Scale: 1M events (local dev), ~20M events (hidden practice), ~60M events (final).
- Shared Devices ("Mega-Persons"): 0.4% of people touch 3 to 6 shared device IDs,
  merging thousands of shoppers into single giant connected components with dense,
  interleaved sessions and clicks.
- Long Link Chains: Some users have 50 to 400 linked IDs chained in random order
  (requires proper Union-Find / connected components, not simple 1-hop joins).
- Unused Smallest IDs: 5% of people have an extra linked ID that never appears in
  events or clicks, which may still be their byte-wise smallest canonical ID.
- Boundary Traps: Gap durations of exactly 30:00.000 vs 30:00.001; clicks at
  exactly 7 days vs 7 days + 1 ms; late events at exactly 24h vs 24h + 1s;
  leap day Feb 29, 2028; duplicated events where only the earliest `ingest_ts`
  is invalid or has a different `user_id`.
